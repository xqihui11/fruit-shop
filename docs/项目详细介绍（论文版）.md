## 1. 项目概述

### 1.1 项目背景与意义

“飘香水果商城”是一个**前后端分离**的水果电商系统，围绕生鲜水果交易的典型流程，提供从“商品浏览—下单—支付—履约—评价/售后—运营与沟通”的完整闭环。项目通过三种角色（**消费者/商家/管理员**）实现多端业务隔离，覆盖电商平台常见能力：商品管理、订单管理、优惠券与公告运营、站内消息与聊天、评价与售后等。

### 1.2 建设目标

- **业务目标**：实现电商核心交易流程闭环，支持多角色协同。
- **技术目标**：采用主流前后端分离架构，形成清晰的分层设计与可维护代码结构。
- **演示与论文目标**：具备可展示的完整功能链路与可描述的架构/数据库/接口/安全方案。

### 1.3 用户角色与边界

- **消费者端（用户端）**：浏览商品/店铺、购物车、下单支付、订单管理、评价、售后申请、收藏、消息与聊天、优惠券与公告等。
- **商家端**：商品与库存/规格维护、订单履约（发货）、售后处理、店铺信息、运营（商家券/公告）、聊天沟通等。
- **管理员端**：平台级用户/商家/商品/分类/订单/售后/运营（公告与优惠券）管理、联系留言处理、聊天沟通等。

## 3. 总体架构设计

### 3.1 架构风格：前后端分离 + 三层后端

系统采用典型的前后端分离架构：

- **前端**负责页面展示、路由组织、交互与状态管理，通过 HTTP 调用后端 API。
- **后端**采用 Controller/Service/Mapper 三层结构：
  - **Controller**：接口入口层，接收参数、做基础校验与组合返回结果
  - **Service**：业务层，承载核心业务规则（下单、支付、售后、权限与数据隔离等）
  - **Mapper**：数据访问层，负责与数据库交互（MyBatis-Plus）


### 3.3 请求流转（从前端到数据库）

1. 前端页面触发行为（如加入购物车、提交订单）。
2. 通过 `frontend/src/utils/api.js` 发起请求，自动设置 `baseURL: '/api'` 并注入 `Authorization: Bearer <token>`（按角色区分 token）。
3. Vite 代理将 `/api` 转发到 `http://localhost:8080`（开发环境）。
4. Spring Boot 接收请求，进入 Controller。
5. 鉴权拦截器解析 JWT，将 userId/role 写入 `UserContext(ThreadLocal)`，Service 层可随时读取当前用户身份。
6. Service 层执行业务逻辑，调用 Mapper 读写数据库。
7. Controller 使用统一返回对象 `Result{code,message,data}` 返回给前端。

## 4. 关键设计：认证与权限

### 4.1 JWT 认证机制

- **签发**：登录成功后由后端生成 JWT，载荷包含 `userId/username/role` 等信息。
- **携带**：前端在请求头中携带 `Authorization: Bearer <token>`。
- **解析**：后端拦截器解析 token 并校验有效期；有效则写入 `UserContext`。

JWT 配置要点（来自 `application.yml`）：

- `jwt.secret`：长度至少 32 字符（满足 HMAC-SHA256）
- `jwt.expiration`：默认 24 小时（86400000ms）

### 4.2 三端鉴权与隔离策略

- **前端路由守卫**：`frontend/src/router/index.js` 通过 `meta.requiresAuth / requiresMerchantAuth / requiresAdminAuth` 拦截未登录访问。
- **前端请求拦截**：`frontend/src/utils/api.js` 根据“当前路径 + 请求 URL 前缀”选择 `token / merchant_token / admin_token` 自动注入。
- **后端身份上下文**：拦截器将 userId/role 写入 `UserContext(ThreadLocal)`，Service 层以此做：
  - 数据归属校验（例如地址属于当前用户、订单属于当前商家等）
  - 权限判断（例如商家接口仅允许 role=merchant）

### 4.3 统一返回与错误处理

后端接口统一返回：

- `code`：成功为 200，失败通常为 500（也可自定义）
- `message`：提示信息
- `data`：业务数据

前端统一响应处理：

- 401：按角色清理本地 token 并跳转到对应登录入口
- 其他错误：统一弹出提示（Element Plus Message）

## 5. 功能模块设计（按业务域）

为便于论文结构化描述，可将系统模块按“业务域”划分如下。

### 5.1 账户与角色模块

- 用户注册/登录、个人信息与登录态维护
- 商家注册/登录、店铺信息维护、审核/状态管理（由管理员或平台规则控制）
- 管理员登录与平台管理权限

关键点：

- 三端 token 分离存储（`token / merchant_token / admin_token`）
- 角色字段 `role` 参与后端权限判断

### 5.2 商品与分类模块

主要能力：

- 分类展示与筛选（如苹果类、核果类等）
- 商品列表、详情、搜索
- 商品规格（如重量/包装等）与不同价格配置
- 商家侧商品上架/下架、库存与销量维护
- 管理员侧商品审核/管理（若业务设定需要）

数据库关联（示例）：

- `products`（商品）— `categories`（分类）
- `product_specs`（规格）— `products`

### 5.3 购物车模块

能力：

- 购物车添加/减少/删除
- 勾选结算（字段 `is_selected`）
- 支持登录用户维度（`user_id`）以及可扩展的会话维度（`session_id`）

实现要点（数据库层面）：

- 购物车唯一约束：`user_id + product_id + spec_id`（或 `session_id + product_id + spec_id`）避免重复行

### 5.4 订单模块（核心交易链路）

订单的关键过程：

1. **确认订单**：选择地址、备注、优惠券（若有），从购物车读取勾选项。
2. **创建订单**：生成订单号与订单主表记录（`orders`），并写入明细（`order_items`）。
3. **支付**：创建支付记录（`payments`），回调/模拟支付成功后更新支付状态与订单状态。
4. **履约**：商家发货填写物流信息，用户确认收货。
5. **评价**：订单完成后可对商品评价；评价可产生消息提醒与互动。

订单状态（以数据库字段为准）：

- `orders.order_status`：0 待支付、1 待发货、2 待收货、3 待评价、4 已完成、5 已取消
- `orders.payment_status`：0 未支付、1 已支付、2 支付失败、3 已退款

### 5.5 支付模块

能力：

- 创建支付记录、防重复创建（幂等思想）
- 支付回调/模拟支付，统一处理成功/失败
- 支付成功驱动订单状态变化，并触发库存/销量更新（业务一致性）

说明：

- 项目包含 `AlipayProperties/AlipayClientConfig` 等配置类，论文中可作为“第三方支付对接的可扩展设计”描述点。

### 5.6 优惠券与运营（公告）模块

能力：

- 平台券与商家券
- 优惠券类型：满减券/折扣券（字段 `type` 区分）
- 领券、我的优惠券、下单核销
- 公告发布（系统/活动/维护）、置顶与目标人群（全部/用户/商家）

核心表：

- `coupons`、`user_coupons`、`announcements`

### 5.7 评价与互动模块

能力：

- 对商品评价（评分、内容、图片等）
- 评价回复、评价点赞
- 对应互动产生站内消息（提醒商家或用户）

核心表：

- `reviews`、`review_likes`、`review_replies`、`messages`

### 5.8 售后模块

能力：

- 退货/退款申请（类型字段区分）
- 商家处理（同意/驳回/完成）
- 用户申诉、管理员介入处理（可体现在售后描述字段中，形成流程闭环）

核心表：

- `after_sales`

### 5.9 消息与聊天模块

能力：

- 站内消息列表、已读状态、消息跳转链接（如跳到订单页/商品页/商家后台评价页）
- 用户与商家聊天：会话表 + 消息表；含未读计数、最近消息与时间
- 支持特殊卡片消息（如订单卡片、商品卡片）以提升沟通效率

核心表：

- `messages`
- `chat_conversation`、`chat_message`

### 5.10 联系我们/留言模块

能力：

- 前台提交咨询/建议/投诉/合作等留言
- 管理端查看并回复，形成闭环

核心表：

- `contact_messages`

## 8. 核心业务流程（可直接写成论文“业务时序”）

### 8.1 登录鉴权流程

1. 用户在统一登录页选择角色并提交账号密码。
2. 后端校验账号密码，签发 JWT（包含 userId/role）。
3. 前端保存 token 到 `localStorage`（按角色区分）。
4. 访问受保护路由时，路由守卫检查 token；请求发出时 Axios 自动注入 `Authorization`。
5. 后端拦截器解析 JWT，将身份写入 `UserContext`，业务层据此做权限与数据校验。

### 8.2 下单与支付流程（交易闭环）

1. 购物车勾选商品，进入结算页选择地址与优惠券。
2. 创建订单：写入 `orders` 与 `order_items`；更新用户券状态；清理已结算购物车项（建议事务保证一致性）。
3. 创建支付记录：避免重复创建；返回支付参数（可为模拟支付或第三方支付参数）。
4. 支付成功回调：更新支付状态与订单状态，并触发库存扣减、销量累加等。
5. 商家发货：填写物流公司与单号，订单变为待收货；同时向用户发送站内消息。
6. 用户确认收货：订单变为待评价/已完成（依业务规则）。

### 8.3 售后流程（退款/退货/申诉）

1. 用户在订单中发起售后（退货或退款），提交原因/描述/凭证。
2. 商家处理申请：同意/驳回；若同意退货则用户填写物流信息。
3. 用户可申诉，管理员介入给出处理结果（可在售后描述中形成记录链）。
4. 结束状态：售后完成（退款完成/退货完成/驳回关闭）。

## 9. 部署与运行说明

### 9.1 本地开发运行

- **数据库**：创建 `fruit_shop` 数据库并导入 `fruit_shop.sql`
- **后端**：
  - 运行 `backend` 的 Spring Boot 应用（IDE 运行启动类或 `mvn spring-boot:run`）
  - 确认 `application.yml` 的数据库端口（默认 `3308`）与账号密码正确
- **前端**：
  - `npm install`
  - `npm run dev`（默认 `3000`），通过 Vite 代理访问后端 `/api`

### 9.2 生产构建（建议写法）

- 前端 `npm run build` 产出 `dist/`，由 Nginx/静态服务器托管
- 通过反向代理将 `/api` 转发到后端 `8080`

### 9.3 文件上传与静态访问

- 上传目录由 `file.upload-path` 指定（例如 `D:/uploads/fruit-shop/`）
- 后端通过静态资源映射暴露 `/uploads/**`（论文中可写成“上传存储与静态资源访问设计”）

## 10. 安全性与可靠性设计（论文加分点）

### 10.1 认证与会话安全

- JWT 过期机制（24 小时）
- 前端 401 统一处理：清理登录态并跳转登录
- Token 按角色隔离存储，降低跨端误用风险

### 10.2 业务一致性与幂等性（建议描述点）

- 下单：建议以事务保证“订单主表/明细/购物车/优惠券”写入一致
- 支付：回调处理按订单与支付状态做幂等，避免重复扣库存、重复更新状态

### 10.3 数据合法性校验

- 地址、订单、售后等关键资源需要校验“归属关系”（userId/merchantId）
- 重要字段（金额、数量、状态）需限制范围与状态机流转

## 11. 测试与验收（可直接写进论文）

建议采用“功能测试 + 接口测试 + 异常测试”的写法：

- **功能测试**：登录、购物车、下单、支付、发货、收货、评价、售后、公告/优惠券、聊天等全流程
- **接口测试**：对关键接口验证入参/出参、权限、边界值（数量为 0、库存不足、优惠券过期等）
- **异常测试**：401 未登录、支付重复回调、非法访问他人订单/地址等

## 12. 可扩展与优化方向（论文总结常用）

- **权限系统**：引入更细粒度 RBAC/权限注解（如 Spring Security）
- **订单超时**：引入定时任务/延时队列实现“未支付自动取消”
- **支付对接**：完善支付宝/微信的真实支付流程与签名验签
- **库存并发**：引入乐观锁/悲观锁或 Redis 预扣库存，提升并发一致性
- **日志审计**：完善 `operation_logs` 的落库与查询，用于后台追踪
- **搜索与推荐**：引入全文检索（如 Elasticsearch）与推荐策略（销量/评价/用户偏好）
